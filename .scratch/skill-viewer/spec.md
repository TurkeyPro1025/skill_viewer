# Spec: 轻量开源 Skill 查看器（skill-viewer）

labels: ready-for-agent
created: 2026-10-14
status: 已确认（设计共识来自 sess_013ec078 的 grilling 轮次 + ChatGPT 方案交叉对比修订 + 开源目标修订）

## Problem Statement（问题陈述）

我用 skills CLI 装了几个知名 Skill 仓库，一个仓库会平铺装出几十个子技能文件夹（如 mattpocock/skills 装出 38 个、ui-ux-pro-max 装出 7 个），装完后它们和独立技能混在一起，"哪个技能属于哪个仓库、各自是干嘛的"完全不可见，查找十分混乱。而且几乎所有技能文档（SKILL.md 及 references 等）都是英文，逐篇阅读很吃力。我需要一个工具把这些已装技能整理清楚、可搜索，并让我能舒服地中英对照阅读文档——但我明确不想为此引入一个重量级的技能"管理器"（安装/卸载/同步）。

## Solution（解决方案）

一个只读优先的本地 Skill 知识库：Node 单文件本地服务 + 网页 UI。打开应用或点"手动更新"时触发分析：多根扫描技能目录（解析 junction/symlink 按真实路径去重），归属引擎以 skills CLI 的安装清单 `.skill-lock.json` 为主表把技能精确归属到"仓库→子技能"两级结构（`.git` remote、frontmatter URL 补充，LLM 读正文推断兜底，手动归组最高优先级）；分类与中文概述由种子数据/LLM 生成并缓存；文档查看器提供块级对齐的左英右中对照阅读（中文原文单栏直出），翻译走 UApiPro AI 翻译接口；全部结果按内容哈希增量缓存为 JSON，未变化的数据永不重复调用 API。项目以 MIT 开源，UI 与服务之间只通过 HTTP JSON API 通信，为将来可能的 Tauri 桌面壳留门。

## User Stories（用户故事）

1. 作为技能用户，我想打开应用时自动扫描配置的所有技能根目录，这样不需要手动导入就能看到全部已装技能。
2. 作为技能用户，我想扫描时自动解析 junction/符号链接并按真实路径合并去重，这样同一技能不会因被链接到 .zcode/.claude 而显示三份。
3. 作为技能用户，我想在技能卡片上看到"被链接到哪些根目录"的徽章，这样我知道它在哪些工具里生效。
4. 作为技能用户，我想点"手动更新"按钮重新触发分析，这样装新技能后不用重启应用。
5. 作为技能用户，我想分析过程有进度显示，这样大扫描时我知道应用没有卡死。
6. 作为技能用户，我想技能按"来源仓库 → 子技能"两级结构展示，这样一个仓库的技能聚在一起，而不是 50 个平级文件夹。
7. 作为技能用户，我想安装清单里有记录的技能自动精确归属到仓库（含仓库内分组信息），这样 ui-ux 7 件套、mattpocock 38 件套零手动操作就归位。
8. 作为技能用户，我想带 `.git` 的技能直接读远端地址归属，这样手动 clone 的技能（如 travel-skill）也能归组。
9. 作为技能用户，我想 frontmatter 带来源 URL 的技能被归属并明确标注"创作上游"，这样不会把上游署名误当安装来源。
10. 作为技能用户，我想无记录的技能由 LLM 读正文推断候选仓库并标注"推断"，这样 to-issues 这类技能大概率自动归位。
11. 作为技能用户，我想手动把技能归入某仓库或"未知来源"组、并一键确认推断结果，这样最终归属由我拍板。
12. 作为技能用户，我想手动归组与确认结果在重新分析后仍然保留，这样我的整理劳动不会被覆盖。
13. 作为技能用户，我想无法归属的技能进入"未知来源"分组且全部功能照常可用，这样归属不完整也不阻塞阅读。
14. 作为技能用户，我想每个技能有中文概述和分类标签，这样不点开英文文档就能判断它是不是我要找的。
15. 作为技能用户，我想知名仓库的概述来自人工整理的种子数据，这样开箱即有高质量首页。
16. 作为技能用户，我想独立技能的概述由 LLM 按统一格式生成（用途/适用场景/主要能力/使用方式/相关分类），这样信息密度一致。
17. 作为技能用户，我想 LLM 服务未接入时概述降级为 frontmatter 描述的机翻，这样第一阶段不依赖 chat API 也可用。
18. 作为技能用户，我想来源归组与分类标签是两套独立数据，这样一个技能可以同时属于"设计工具"和"UI 开发"两个分类。
19. 作为技能用户，我想按名称/描述/分类/仓库名搜索过滤技能列表，这样几十个技能里能秒找到目标。
20. 作为技能用户，我想点开技能弹出文档查看器，左侧英文原文、右侧中文译文，这样能逐段对照阅读。
21. 作为技能用户，我想原文与译文按内容块（标题/段落/列表）一一对应且滚动联动，这样长文档里不迷失位置。
22. 作为技能用户，我想中文原文的文档直接单栏展示、不调翻译，这样不浪费额度也不别扭。
23. 作为技能用户，我想代码块、命令、URL、文件路径、环境变量保持原文不被翻译改写，这样技术内容不被破坏。
24. 作为技能用户，我想入口 SKILL.md 在分析时批量预翻译、附属文档首次打开时才翻译，这样额度花在刀刃上。
25. 作为技能用户，我想查看器侧栏目录树列出技能内全部 .md 文档并支持图片内联展示，这样附属参考文档也能读。
26. 作为技能用户，我想译文和概述按内容哈希缓存，这样内容没变的文档永不重复调用 API。
27. 作为技能用户，我想技能升级后（内容哈希变化）自动重新生成概述和入口译文，这样缓存不会陈旧。
28. 作为技能用户，我想首次翻译前应用明确告知文档内容将发送到外部 API，这样隐私知情权有保障。
29. 作为技能用户，我想扫描根目录与 provider 全部可配置、无硬编码路径，这样 macOS/Linux 用户也能使用。
30. 作为技能用户，我想 API key 不落明文配置文件（环境变量或系统凭据存储），这样密钥安全。
31. 作为开源贡献者，我想归属引擎是独立模块且支持注册新的安装清单格式，这样我能为新安装器贡献适配。
32. 作为开源贡献者，我想翻译/LLM provider 是干净的适配器接口，这样我能贡献新的翻译或摘要服务。
33. 作为开源贡献者，我想测试通过 HTTP API 单缝黑盒进行（fixture 技能树 + stub provider），这样贡献者不需要真实 API key 就能跑通全部测试。

## Implementation Decisions（实现决策）

- **形态**：Node 单文件本地服务 + 静态网页 UI；启动即扫描、伺服页面与 API。网页 UI 与服务之间只通过 HTTP JSON API 通信，UI 不持有任何 Node 特有能力——这是给未来 Tauri sidecar 壳留的门。
- **模块划分**：扫描器（多根扫描、junction/symlink 解析、SKILL.md frontmatter 解析）、归属引擎、翻译管线、缓存层、provider 适配器、HTTP API 层。
- **归属引擎**（本项目最大亮点，必须独立成模块）：瀑布式策略——① `.skill-lock.json`（skills CLI 安装清单，按文件夹名 join，含来源仓库/仓库内路径/内容哈希/安装时间）② `.git` remote ③ frontmatter URL（标注"创作上游"而非安装来源）④ LLM 读正文推断（标注"推断"待确认）⑤ `overrides.json` 手动归组，优先级最高。引擎接口支持注册新的清单格式识别器。
- **去重**：多根扫描后解析链接取真实路径，同一实体合并为一条；真实路径不同但内容一致的独立拷贝也合并；内容分岔则作为两个版本分别展示。
- **翻译 provider**：UApiPro（uapis.cn）`POST /api/v1/ai/translate`，固定参数 `target_lang=zh, style=professional, context=technical, preserve_format=true`；单次 1 万字符上限、4 QPS 节流、按次计积分。长文分块。
- **翻译管线**：解析 Markdown 为内容块（标题/段落/列表/引用/代码块），每块分配稳定 ID；frontmatter 与代码块占位摘出、译后回填；译文块与原文块按 ID 关联，供查看器并排渲染。代码、命令、路径、URL、环境变量一律不译。
- **概述生成**：两级——知名仓库用人工种子数据（ui-ux-pro-max 与 mattpocock/skills 的种子已备好）；独立技能由 LLM provider 生成统一格式（用途/适用场景/主要能力/使用方式/相关分类）。LLM provider 预留 OpenAI 兼容接口（base URL + key + model），规划接 DeepSeek 或 GLM；未接入时降级为 frontmatter 描述的机翻。UApiPro 翻译接口不得充当摘要模型。
- **缓存**：JSON 拆分存储——索引文件（快速加载列表）、仓库映射文件、每技能一文件（分类/概述）、译文按技能+文档分文件；每份缓存记录源文档内容哈希、所用 provider、缓存版本。缓存键 = 技能真实路径 + 内容哈希；哈希变化才重新生成概述/重翻入口文档。
- **触发时机**：应用启动时与"手动更新"按钮；其余时间纯读缓存，零 API 调用。
- **配置与安全**：config 只存非敏感配置（扫描根列表、provider 端点/模型名）；API key 走环境变量或操作系统凭据存储，绝不写入缓存或明文配置。首次翻译前向用户提示文档内容将上传外部 API。
- **语言处理**：原文为中文 → 单栏直出不翻译；来源归组与分类标签是两套独立数据（一技能可属多分类）。
- **交付顺序**（三阶段）：① 扫描/归属/分类/搜索（零 API 依赖，先解决"找不到"）② 翻译与对照阅读器（解决"看不懂"）③ 指纹增量、推断置信度展示、失败重试。
- **范围红线**：v1 不含插件缓存目录的技能（zcode 官方 17 插件，未来可加"插件"分组）；不做安装/卸载/同步管理；不实现桌面打包；不做"仓库特征库"模糊匹配（已明确否决——lock 文件存在使其冗余）。
- **开源**：MIT，npx 分发为目标，README 突出 lock 归属引擎卖点。

## Testing Decisions（测试决策）

- **唯一测试缝：本地服务的 HTTP API**（用户已确认）。好测试只断言外部可见行为——API 响应与缓存文件产物，不断言模块内部实现细节。
- **测试装置**：fixture 技能树，需覆盖——多根目录、junction/symlink、有/无 lock 条目、带 `.git` 的技能、frontmatter 带 URL、中文文档、英文长文档（触发分块）、同名不同内容（版本分岔）、内容变更（哈希变化触发重处理）。
- **provider 打桩**：配置指向本地 stub HTTP 服务（fake UApiPro / fake LLM），全部测试不打真网、不需要真实 key——这也是开源贡献者的体验要求（故事 33）。
- **UI 不设测试缝**：手动验收清单 + 一条冒烟检查（首页渲染、查看器可打开）。
- **先例**：绿地项目无先例，本 spec 的测试即项目首批测试。

## Out of Scope（不做）

- 技能的安装、卸载、更新、多工具同步、preset、备份（不做管理器，保持只读）
- skills-manager 底座复用（仅借鉴其未合并 PR #342 的翻译缓存设计思路）
- 插件缓存技能的展示（v1）
- Tauri 桌面打包（只留架构门，不实现）
- 中英以外的语言对（只做英→中；中文原文直出）
- 用户系统、云端同步、SQLite 等非 JSON 存储
- 仓库特征库/模糊匹配机制（被磁盘事实证伪的方案）

## Further Notes（补充说明）

- 磁盘事实基线（2026-10-14 勘察）：`.agents\skills` 为唯一实体（52 文件夹），`.zcode\skills` 全为 junction，`.claude\skills` 为 symlink + 6 真实拷贝；`.agents\.skill-lock.json` 为 v3 格式，覆盖 47/52；5 个无记录技能：caveman、build-to-learn、frontend-design、to-issues、to-prd。
- 种子概述数据来源：会话 sess_2dcd0add（ui-ux-pro-max 七技能与 mattpocock 仓库的中文概述原文）。
- UApiPro 接口细节：见 https://uapis.cn/docs/api-reference/post-ai-translate （10k 字符/次、4 QPS、4 积分/次）。
- lock 文件格式参考 vercel-labs skills CLI；归属优先级与"创作上游 vs 安装来源"的区分是刻意设计（如 pr 技能的 URL 指向 humanlayer 而安装来源是 mattpocock/skills）。
